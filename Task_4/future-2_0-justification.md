# Обоснование перехода на событийную архитектуру

## Проблемы текущей архитектуры (Camel + DWH)

| Проблема | Описание | Следствия |
|:---|:---|:---|
| **Централизованное узкое горлышко** | Все данные проходят через DWH и ESB | При росте нагрузки система тормозит; отчёты формируются часами |
| **Высокая связанность** | Изменение в одном домене требует изменений в DWH и ESB | Time-to-market новых фич - недели и месяцы |
| **Синхронная интеграция** | Сервисы вызывают друг друга синхронно через ESB | При сбое одного сервиса падает вся цепочка |
| **Нет истории событий** | ESB не хранит события после доставки | Нельзя переиграть события, сложно отлаживать, нет аудита |
| **Смешение медицинских и финансовых данных** | Все данные в одном DWH | Регуляторные риски, сложность разграничения доступа |

## Преимущества событийной архитектуры (Kafka + Data Mesh)

### 1. Гибкость

- Добавление нового домена: новый домен подписывается на реплицированные события.
- Домен меняет свою логику независимо.
- A/B тестирование: можно направить часть событий на тестовый consumer.

### 2. Масштабируемость 
- Рост объёма данных: Kafka партиционируется, consumer-ы масштабируются.
- Пиковые нагрузки: Kafka буферизует, consumer-ы читают в своём темпе.
- Геораспределение: региональные кластеры + MirrorMaker

### 3. Скорость реакции
- Время формирования отчёта: секунды (витрины + кэш + потоковые агрегаты).
- Неблокирующие реакции на события.
- Восстановление после сбоя: перечитывание из Kafka с последнего offset.

### 4. Надёжность и отказоустойчивость 
- Отказ одного сервиса: остальные работают, события накапливаются.
- Потеря данных: Kafka хранит на диске, реплицирует.
- Аудит и отладка: все события хранятся, можно переиграть.

### 5. Соблюдение регуляторных требований
- Медицинские данные: изолированы в Medicine Domain.
- Каждое событие логируется.
- Данные могут пересекать границы: географическая привязка кластеров.

## Архитектурные принципы целевой системы

### 1. Каждый домен пишет в свой Kafka-кластер
Ни один домен не имеет прямого доступа к чужому кластеру.

### 2. Междоменные взаимодействия - только через репликацию
Данные передаются через MirrorMaker (partial replicates). На схемах это обозначено пунктирными стрелками.

### 3. Внутри домена - прямые вызовы между контекстами
На схемах обозначено сплошными стрелками.

### 4. Medicine Domain изолирован
- Медицинские данные не покидают домен. Наружу публикуются только обезличенные агрегаты.
- Медицинские данные (истории болезней, диагнозы, результаты исследований) подлежат особой защите.


## Ключевые метрики успеха

| Метрика | Целевое значение |
|:---|:---|
| Time-to-market нового домена | < 2 недель |
| Время формирования отчёта | < 10 секунд |
| Доступность событийной платформы | 99.9% |
| Потеря данных при сбое | 0 |
| Кросс-доменных инцидентов | 0 в месяц |

## Вывод

Переход с синхронной интеграции через ESB/DWH на асинхронную событийную архитектуру на базе Kafka и Data Mesh позволяет компании «Будущее 2.0»:

- **Быстрее выводить на рынок новые продукты**
- **Масштабироваться горизонтально**
- **Обеспечить соблюдение регуляторных требований**
- **Повысить отказоустойчивость**
- **Улучшить наблюдаемость**
